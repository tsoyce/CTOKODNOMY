# Node.js-приложение в BrainyCP

Для этого проекта выбирайте **Node.js**, версию **24**. Один сервер Node.js обслуживает API, WebSocket и собранный интерфейс React. Отдельное приложение React или Next.js не требуется.

Все адреса, имена и пути ниже — примеры. Замените `/home/appuser/sites/game`, `appuser`, `game.example.ru` и порт `3000` значениями своего экземпляра. Они хранятся в настройках панели и серверном `.env`; менять исходники для другого домена или порта не нужно.

Для проверенной конфигурации BrainyCP доступен сценарий **Deploy BrainyCP (manual)**. Ниже также описана ручная установка из архива **Build BrainyCP release (manual)**. Альтернативный сценарий **Deploy Docker (manual)** предназначен для размещения через Docker и описан в [DEPLOYMENT.md](DEPLOYMENT.md).

### Проверка доступа перед размещением

**Actions → BrainyCP server check (manual)** проверяет сервер через уже сохранённый `DEPLOY_SSH_KEY`. В форме укажите SSH-сервер и пользователя, каталог приложения, пользователя процесса, порт и домен без схемы. Значения конкретного экземпляра остаются вне исходников. Нужен также секрет `SSH_KNOWN_HOSTS` с проверенным публичным ключом сервера; как получить его через доверенное SSH-подключение, описано в [DEPLOYMENT.md](DEPLOYMENT.md#3-настройки-github-actions).

Проверенную публичную запись можно также передать в поле `known_hosts` этой формы: оно имеет приоритет над секретом. На Windows существующую запись доверенного подключения показывает `ssh-keygen -F SERVER_HOST -f "$env:USERPROFILE\.ssh\known_hosts"`. Это публичный ключ сервера, отдельный от приватного ключа пользователя, который хранится только в `DEPLOY_SSH_KEY`.

Проверка выводит метаданные только каталога приложения, доступные версии Node.js, статус локального порта, версию PostgreSQL при доступном соединении и пути конфигураций нужного сайта. Она не читает `.env`, не меняет права или настройки, не создаёт БД и не запускает процессы. Её результаты нужны для выбора фактических настроек BrainyCP; успешная проверка SSH ещё не означает размещение сайта.

### Выкладка через Actions

**Deploy BrainyCP (manual)** поддерживает проверенный вариант: Linux x86_64, существующая служба `nodejs@PORT.service` с рабочей папкой этого приложения, Nginx с отдельным файлом домена, PostgreSQL на локальном порту 5432 с административным peer-доступом и установленный Certbot. Службы с `RootDirectory` требуют другого адаптера. Сначала выполните проверку сервера, затем укажите те же значения в форме деплоя.

Сценарий проверяет код и браузерный сценарий, собирает React/сервер и переносит их через SSH. Node.js 24 устанавливается отдельно в `/opt/ctokodnomy-node` из официального архива с проверкой SHA-256. Системный Node других приложений не заменяется. Выпуск и зависимости принадлежат пользователю приложения; запуск меняется через отдельный systemd drop-in только для указанного порта.

Для первого размещения создаются выделенные БД и роль `ctokodnomy_USER_PORT`, приватные настройки `~/.config/ctokodnomy/native-PORT.env` и изображения в `~/.local/share/ctokodnomy/PORT/uploads`. Пароль генерируется на сервере и не выводится. Перед миграциями сохраняются копия БД и прежние настройки приложения. Каталоги выпусков находятся в корне сайта, а `current` указывает на активный выпуск. Существующие файлы шаблона панели сохраняются.

Для указанного домена выпускается сертификат Let's Encrypt. Nginx передаёт запросы на `127.0.0.1:PORT`, поддерживает WebSocket и перенаправляет HTTP на HTTPS. Меняется только файл этого домена; конфигурация проверяется до reload. При ошибке запуска восстанавливаются предыдущая служба и конфигурация сайта; БД автоматически не откатывается.

При обновлении завершите игровую активность. Новый push запускает проверки, а размещение запускается явно. Повторная отправка того же SHA не перезаписывает существующий выпуск: сначала проверьте его состояние. Не меняйте параметры Node-приложения в панели во время деплоя; панель управляет исходной службой, а наш drop-in задаёт рабочий выпуск и отдельный runtime.

После первого успешного размещения одноразовый код установки можно получить с Windows:

```powershell
ssh -o IdentitiesOnly=yes -i "$env:USERPROFILE\.ssh\codex_deploy" root@server.example.com "cd /home/appuser/sites/game/current && /home/appuser/sites/game/shared/runtime/node24/bin/node dist/server/cli.js setup-token"
```

Замените адрес и путь значениями экземпляра. Введите код на странице `/setup`, создайте администратора и настройте брендинг. Этот код выводится только в вашей консоли, действует час и не сохраняется в GitHub Actions.

## 1. Настройки приложения в панели

Создайте приложение Node.js под отдельным пользователем сайта и выберите Node.js 24. Ожидаемая конфигурация:

| Настройка             | Пример                                           |
| --------------------- | ------------------------------------------------ |
| Корень приложения     | `/home/appuser/sites/game`                       |
| Пользователь процесса | `appuser`                                        |
| Версия Node.js        | `24.x`                                           |
| Внутренний порт       | `3000`, либо свободный порт, назначенный панелью |
| Файл запуска          | `current/app.mjs`                                |
| Число процессов       | `1`, режим cluster выключен                      |
| Публичный адрес       | `https://game.example.ru`                        |

Названия полей зависят от версии BrainyCP. Приложение должно работать одним процессом: рассылка изменений WebSocket хранится в его памяти. Если панель умеет запускать только файл `app.mjs` в корне, после подготовки первого выпуска можно создать ссылку `app.mjs -> current/app.mjs`. Перед этим проверьте, что в корне нет существующего файла с таким именем; его не следует перезаписывать.

Настройте HTTPS для сайта и проксирование к локальному порту приложения. Для живого обновления табло прокси должен поддерживать WebSocket; проверьте соответствующую настройку BrainyCP. Внешний доступ к порту Node.js и PostgreSQL не требуется. Не меняйте конфигурацию остальных сайтов.

Ключ, добавленный в `/root/.ssh/authorized_keys`, разрешает вход как `root`. Для входа по SSH как `appuser` публичный ключ нужно отдельно добавить этому пользователю. Само наличие пользователя приложения такого доступа не даёт.

## 2. Отдельная база PostgreSQL

Если PostgreSQL уже установлен, создайте в разделе баз данных BrainyCP **отдельную БД и пользователя игры**. Выдайте этому пользователю владение своей БД: приложение создаёт таблицы и применяет миграции при запуске. Права суперпользователя PostgreSQL для приложения не нужны.

Запишите фактические имя БД, пользователя, порт и пароль в серверные настройки. Панель может добавлять префикс к именам. Проект проверен с PostgreSQL 17; версию работающего сервера можно посмотреть в SQL-консоли командой `SHOW server_version;`.

Если панель не предоставляет создание PostgreSQL-БД, администратор может выполнить в интерактивной консоли `psql`:

```sql
CREATE ROLE game_app LOGIN;
\password game_app
CREATE DATABASE game_db OWNER game_app;
```

Команда `\password` запросит пароль отдельно и скроет ввод. Это команды внутри `psql`, а не PowerShell. Для обычной установки PostgreSQL с системным пользователем `postgres` root может открыть такую консоль командой `runuser -u postgres -- psql`; в другой установке используйте предусмотренный администраторский доступ. Не меняйте пароль или права пользователей других сайтов.

## 3. Постоянные настройки и изображения

На сервере сначала проверьте корень приложения, созданный панелью:

```sh
game_root=/home/appuser/sites/game
game_user=appuser
ls -la "$game_root"
```

Для первого размещения создайте новые каталоги. Если они уже существуют, проверьте их содержимое и продолжайте с подготовленной структурой:

```sh
(
  set -eu
  mkdir "$game_root/releases" "$game_root/shared" "$game_root/backups"
  chown "$game_user:" "$game_root/releases" "$game_root/shared" "$game_root/backups"
  chmod 750 "$game_root/releases"
  chmod 700 "$game_root/shared" "$game_root/backups"
)
```

Перейдите в консоль пользователя приложения: root может выполнить `su - appuser`. Затем создайте настройки и каталог загрузок:

```sh
game_root=/home/appuser/sites/game
umask 077
mkdir "$game_root/shared/uploads"
nano "$game_root/.env"
```

Содержимое `.env`:

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=3000
APP_ORIGIN=https://game.example.ru
DATABASE_URL=postgresql://game_app:REPLACE_WITH_PASSWORD@127.0.0.1:5432/game_db
MEDIA_DIR=/home/appuser/sites/game/shared/uploads
TRUST_PROXY=1
```

Замените порт значением из панели, адрес — настоящим HTTPS-адресом, реквизиты — своей БД. `APP_ORIGIN` содержит схему и имя хоста без пути; нестандартный внешний порт также входит в адрес. `MEDIA_DIR` должен быть абсолютным путём вне каталогов выпусков, чтобы обновление сохраняло загруженные изображения. `TRUST_PROXY=1` подходит, когда приложение доступно только через доверенный локальный прокси панели и слушает `127.0.0.1`.

Пароль в `DATABASE_URL` требуется URL-кодировать, если в нём есть, например, `@`, `:`, `/`, `#` или `%`. Для нового пароля можно выбрать случайную шестнадцатеричную строку и задать её той же роли в БД. Не отправляйте пароль, `.env` или приватный SSH-ключ в чат и не добавляйте их в Git.

После сохранения:

```sh
chmod 600 "$game_root/.env"
```

Файл должен принадлежать пользователю приложения. Node.js читает `.env` сам: не выполняйте `source .env` и не запускайте его как shell-скрипт. Переменные, которые панель уже передала процессу, имеют приоритет над `.env`; избегайте противоречащих значений.

## 4. Получение и подготовка выпуска

В GitHub откройте **Actions → Build BrainyCP release (manual) → Run workflow**, выберите `main`. После успешных проверок скачайте артефакт **ctokodnomy-native** и распакуйте скачанный ZIP на компьютере. В нём находятся:

```text
ctokodnomy-native.tar.gz
ctokodnomy-native.tar.gz.sha256
COMMIT.txt
```

Архив содержит `app.mjs`, `package.json`, `package-lock.json`, собранные `dist/client` и `dist/server`. Настройки, загрузки и `node_modules` в него не включены. `COMMIT.txt` указывает проверенный коммит. Для локальной сборки из репозитория используйте `npm ci` и `npm run package:native`; результат находится в `dist/`.

Из PowerShell, находясь в папке с распакованными файлами артефакта:

```powershell
$releaseId = (Get-Content -Raw .\COMMIT.txt).Trim()
ssh -o IdentitiesOnly=yes -i "$env:USERPROFILE\.ssh\codex_deploy" root@server.example.com "mkdir -m 700 /tmp/ctokodnomy-$releaseId"
scp -o IdentitiesOnly=yes -i "$env:USERPROFILE\.ssh\codex_deploy" .\ctokodnomy-native.tar.gz .\ctokodnomy-native.tar.gz.sha256 .\COMMIT.txt "root@server.example.com:/tmp/ctokodnomy-$releaseId/"
```

Новый каталог не перезаписывает предыдущий выпуск. При повторной отправке того же коммита сначала проверьте уже созданный каталог. На сервере, как root, замените `COMMIT_SHA_FROM_FILE` содержимым `COMMIT.txt` и выполните:

```sh
game_root=/home/appuser/sites/game
game_user=appuser
release_id=COMMIT_SHA_FROM_FILE
incoming_dir="/tmp/ctokodnomy-$release_id"
release_dir="$game_root/releases/$release_id"
(
  set -eu
  cd "$incoming_dir"
  sha256sum --check ctokodnomy-native.tar.gz.sha256
  mkdir "$release_dir"
  tar --extract --gzip --file ctokodnomy-native.tar.gz --directory "$release_dir" --no-same-owner
  chown -R "$game_user:" "$release_dir"
)
```

Продолжайте после успешной проверки контрольной суммы. Затем снова перейдите в консоль `appuser`. Используйте **именно Node.js 24, выбранный в панели**: путь к его каталогу `bin` возьмите из настроек BrainyCP, если он отличается от Node.js в обычной SSH-консоли.

```sh
export PATH="/path/to/node24/bin:$PATH"
node --version
npm --version
game_root=/home/appuser/sites/game
release_id=COMMIT_SHA_FROM_FILE
release_dir="$game_root/releases/$release_id"
(
  set -eu
  cd "$release_dir"
  npm ci --omit=dev
  ln -s "$game_root/.env" "$release_dir/.env"
)
```

`node --version` должен показать `v24...`. Установка выполняется под пользователем сайта, чтобы зависимости и приложение принадлежали ему. Сборку на сервере запускать не требуется. Для последующих обновлений подготовьте новый каталог и зависимости до остановки работающей игры.

## 5. Первый запуск и мастер установки

Для первого выпуска, под пользователем приложения, создайте ссылку:

```sh
ln -s "$release_dir" "$game_root/current"
```

Выберите в BrainyCP файл запуска `current/app.mjs` и запустите приложение средствами панели. Обёртка `app.mjs` выбирает рабочий каталог своего выпуска, поэтому приложение находит его `.env` и собранный интерфейс даже при другом исходном рабочем каталоге процесса. Если настройка панели требует корневой `app.mjs`, создайте описанную в первом разделе ссылку после проверки отсутствия такого файла:

```sh
ln -s current/app.mjs "$game_root/app.mjs"
```

Проверьте локальный порт и затем сайт с компьютера или телефона:

```sh
curl --fail http://127.0.0.1:3000/api/health
```

Используйте свой порт. Исправное приложение отвечает `{"ok":true}`. В панели проверьте журнал процесса, а в браузере — главную по HTTPS. При запуске приложение применяет миграции к своей БД.

Для первого входа выполните под пользователем сайта с выбранным Node.js 24:

```sh
cd /home/appuser/sites/game/current
node dist/server/cli.js setup-token
```

Откройте `/setup` на сайте и введите выданный токен. Он действует один час. Создайте администратора и настройте название, цвета и логотипы; после этого мастер установки закрывается. Не публикуйте токен в переписке или скриншотах.

Проведите пробную игру: табло на экране гостей, пульт ведущего и телефоны обеих команд. Проверьте предложения участников, отправку капитаном, раскрытие ответа, ошибки, перехват, паузу и восстановление после обновления страницы. Это одновременно проверит WebSocket через прокси и сеть площадки.

## 6. Обновление, резервирование и восстановление

Push в GitHub запускает проверки кода. Сервер обновляется после подготовки нового архива и переключения выпуска через панель.

Перед обновлением сохраните БД и изображения. Копию БД можно создать под пользователем сайта в интерактивной SSH-консоли:

```sh
game_root=/home/appuser/sites/game
backup_file="$game_root/backups/before-$(date -u +%Y%m%dT%H%M%SZ).dump"
(set -o noclobber; umask 077; pg_dump --host 127.0.0.1 --port 5432 --username game_app --dbname game_db --format custom --password > "$backup_file")
```

Подставьте свои реквизиты. `pg_dump` запросит пароль скрытым вводом; пароль не передаётся аргументом команды. Версия `pg_dump` должна поддерживать установленную версию PostgreSQL. Проверьте успешное завершение и сохраняйте копию вместе с `shared/uploads` в отдельном защищённом месте. До мероприятия проверьте восстановление на отдельной тестовой БД.

Порядок обновления:

1. Скачайте проверенный артефакт, проверьте SHA-256, распакуйте новый выпуск, установите его зависимости и создайте ссылку на постоянный `.env`.
2. Завершите игровую активность и остановите приложение через BrainyCP. Не переключайте файлы во время партии.
3. Сделайте свежую резервную копию БД и загрузок **до запуска нового выпуска**: запуск может применить миграции.
4. Под пользователем сайта переключите `current` на подготовленный выпуск командой ниже, затем запустите приложение через панель.
5. Проверьте `/api/health`, публичный сайт, вход ведущего и обновления табло с телефона.

Для переключения существующей ссылки на Linux:

```sh
test -L "$game_root/current" && ln -sfnT "$release_dir" "$game_root/current"
```

Если `current` оказался обычным файлом или каталогом, выясните его назначение вместо перезаписи. Постоянные `.env` и `shared/uploads` между выпусками сохраняются.

Журнал и состояние процесса смотрите в BrainyCP. Для сброса пароля администратора в консоли пользователя сайта:

```sh
cd /home/appuser/sites/game/current
node dist/server/cli.js reset-password YOUR_ADMIN_USERNAME
```

CLI запросит новый пароль скрытым вводом; существующие сеансы администратора будут отозваны.

Не удаляйте предыдущий выпуск сразу после обновления. Возврат ссылки на старый код возможен после проверки совместимости схемы БД: новые миграции могли уже выполниться. Восстановление старой копии БД возвращает состояние на момент копирования, поэтому автоматического отката БД нет.
