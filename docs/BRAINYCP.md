# Node.js-приложение в BrainyCP

Для этого проекта выбирайте **Node.js 24**. Один процесс обслуживает API, WebSocket и собранный интерфейс React. Отдельное приложение React или Next.js не требуется.

Все адреса, имена и пути ниже — примеры. Замените `/home/appuser/sites/game`, `appuser`, `game.example.ru` и порт `3000` настройками своего экземпляра. Домен и реквизиты сервера задаются при размещении, исходники для этого менять не нужно.

**Deploy BrainyCP (manual)** обновляет уже установленное и работающее приложение. Первичную подготовку сервера выполняет администратор отдельно, по разделу ниже. Автоматическая выкладка больше не устанавливает Node.js, не создаёт БД, не выпускает сертификаты и не перенастраивает веб-сервер или systemd.

## Обновление через Actions

Перед обновлением завершите игровую активность. Push запускает проверки кода; **выкладка запускается только вручную** через **Actions → Deploy BrainyCP (manual)**, ветка `main`.

В форме нужны:

| Поле | Что указать |
| --- | --- |
| `server`, `ssh_user` | SSH-сервер и пользователь с UID 0: текущему адаптеру нужен root-доступ для закрытых резервных копий и службы игры |
| `app_root`, `app_user` | Существующий физический корень приложения и пользователь процесса |
| `port`, `domain` | Порт существующей службы `nodejs@PORT.service` и домен игры без схемы |
| `node_bin` | Абсолютный физический путь к уже установленному исполняемому файлу Node.js 24, например `/opt/ctokodnomy-node/node-v24.x.y-linux-x64/bin/node`; символическая ссылка не подходит |
| `php_checks` | От 1 до 10 HTTPS-адресов работающих динамических PHP-страниц, через запятую |
| `known_hosts` | Проверенная публичная запись сервера; можно пропустить, если настроен секрет `SSH_KNOWN_HOSTS` |

В `php_checks` выбирайте конечный адрес PHP-страницы, которая действительно исполняется через PHP. Например, `https://php.example.ru/status.php`. Статическая главная страница не проверит PHP-FPM. Адрес должен сразу отвечать `2xx`, без перенаправлений, авторизации, нестандартного порта, параметров запроса и фрагмента. Несколько адресов позволяют проверить разные сайты и используемые версии PHP. Содержимое ответа отбрасывается; его текст не попадает в журнал.

Для SSH используется секрет `DEPLOY_SSH_KEY` и, если нужен, `DEPLOY_SSH_PASSPHRASE`. Приватный ключ и серверные `.env` не добавляйте в Git. Как сохранить проверенный публичный ключ сервера, описано в [DEPLOYMENT.md](DEPLOYMENT.md#3-настройки-github-actions). На Windows существующую запись доверенного подключения показывает:

```powershell
ssh-keygen -F SERVER_HOST -f "$env:USERPROFILE\.ssh\known_hosts"
```

### Условия запуска

Сценарий рассчитан на Linux и подготовленное приложение со следующей конфигурацией:

- В `/etc/brainy/conf/server_control/main` есть ровно одна действующая непустая настройка `back_server`. Поддерживаются запись через `=` или пробел и одно значение, при необходимости в парных кавычках; закомментированная строка не учитывается. Отсутствие, дубликат или неоднозначная запись останавливает выкладку ещё до создания каталога для загрузки. Сценарий только читает этот файл и никогда его не исправляет.
- `current` — ссылка на существующий выпуск в `APP_ROOT/releases/COMMIT_SHA`, где SHA состоит из 40 шестнадцатеричных символов. До обновления доступны локальный `/api/health` и публичный HTTPS-адрес игры.
- Уже существует и работает `nodejs@PORT.service`. Её `User` совпадает с `app_user`, `RootDirectory` пуст, `WorkingDirectory` равен `APP_ROOT/current`, `ExecStart` запускает указанный физический `node_bin` с `APP_ROOT/current/app.mjs`.
- `EnvironmentFile` службы указывает на существующий закрытый файл `APP_HOME/.config/ctokodnomy/native-PORT.env`. Поддерживается только описанный ниже формат управляемой конфигурации: отдельная роль и БД `ctokodnomy_USER_PORT` на `127.0.0.1:5432`, пароль из 64 строчных шестнадцатеричных символов и фиксированный каталог изображений. Другие работающие установки требуют отдельного адаптера; сценарий не переписывает их настройки.
- Прокси игры заранее настроен администратором в отдельном файле `/etc/nginx/conf.d/DOMAIN-game.conf`, например `/etc/nginx/conf.d/game.example.ru-game.conf`. HTTPS и WebSocket уже работают. Сценарий проверяет и сохраняет этот файл, но не изменяет его.
- Все указанные PHP-страницы отвечают `2xx` до обновления.

Файлы в `sites-available` и другие конфигурации, которыми управляет BrainyCP, нельзя использовать для ручных вставок игры: панель может пересоздать их. Сам сценарий не пишет ни в `sites-available`, ни в `conf.d`, ни в `/etc/brainy`, не создаёт drop-in systemd и не меняет ссылки на runtime. Подготовку или исправление этих настроек выполняют отдельно, после резервирования и проверки устройства конкретного сервера.

### Что происходит при обновлении

Actions проверяет код и браузерный сценарий, собирает архив и проверяет его SHA-256. На сервере сначала проверяются состояние панели, существующая конфигурация приложения и PHP-страницы. Выпуск распаковывается в новый каталог `releases/COMMIT_SHA`, зависимости устанавливаются под пользователем приложения. Существующий выпуск с тем же SHA не перезаписывается.

Каждый запуск и повтор GitHub Actions загружает файлы в отдельный приватный каталог `/var/lib/ctokodnomy-deploy/USER-PORT/COMMIT_SHA-RUN_ID-ATTEMPT`. Незавершённые загрузки сохраняются для диагностики и не перезаписываются. Общая блокировка выкладки и каталог резервных копий остаются в `USER-PORT`. Автоматических повторов передачи нет: перед новым запуском после ошибки нужно проверить состояние сервера и причину сбоя; уже подготовленный выпуск с тем же SHA по-прежнему блокирует повторную активацию.

До переключения сохраняются прежняя цель `current`, настройки приложения, файл прокси, конфигурация панели, сведения о службе и копия БД. Резервные копии находятся в `/var/lib/ctokodnomy-deploy/USER-PORT/backups/TIMESTAMP-SHA` под управлением root, закрыты от других пользователей и недоступны для изменения процессом игры. Их содержимое и реквизиты БД в Actions не выводятся. Копию изображений и внешнюю копию резервов администратор организует отдельно.

Перед активацией повторно проверяется `back_server`. Переключается только `current`, перезапускается только `nodejs@PORT.service`. Затем проверяются локальный и публичный адреса игры, конфигурация панели и те же PHP-страницы. HTTP-статус каждой PHP-проверки должен совпасть с исходным успешным статусом. Nginx, Apache и PHP-FPM не перезапускаются и не перезагружаются; `certbot`, `apt`, `systemctl daemon-reload` и создание БД не выполняются.

Если после переключения возникает ошибка, сценарий возвращает прежний `current` и перезапускает только службу игры. Настройки панели, прокси и systemd из резервов автоматически не восстанавливаются, потому что сама выкладка их не меняет. БД также не откатывается: запуск нового кода мог уже применить миграции, совместимость старого кода со схемой нужно проверить отдельно.

Резервные файлы копируются обычным `cp`; архив передаётся от пользователя приложения через `cat` и распаковывается `tar`. До распаковки проверяются SHA-256 и допустимое содержимое архива. `SIGKILL` или код `137` означает аварийное прерывание. Сценарий не заменяет убитую утилиту обходной реализацией и не продолжает выкладку. При убийстве самого shell обработчик отката выполнить невозможно; перед повторным запуском администратор должен проверить `current`, службу, БД и состояние сервера. Частично подготовленный выпуск не удаляется автоматически.

## Первичная установка администратором

Этот раздел описывает отдельную подготовку нового экземпляра. Ручная выкладка через Actions не выполняет эти действия. На сервере с другими сайтами сначала сохраните конфигурацию BrainyCP, веб-серверов и служб, проверьте резервные копии БД и доступность существующих PHP-сайтов. Если `back_server` отсутствует или процессы получают необъяснённый `SIGKILL`, сначала восстановите и проверьте сервер.

### 1. Приложение, runtime и прокси

В BrainyCP создайте приложение **Node.js 24** под отдельным пользователем сайта с одним процессом; режим cluster выключен. Узнайте фактические пути, порт и устройство службы. Например:

| Настройка | Пример |
| --- | --- |
| Корень приложения | `/home/appuser/sites/game` |
| Пользователь процесса | `appuser` |
| Внутренний порт | `3000` |
| Рабочий каталог службы | `/home/appuser/sites/game/current` |
| Файл запуска | `/home/appuser/sites/game/current/app.mjs` |
| Публичный адрес | `https://game.example.ru` |

Для последующих обновлений служба должна соответствовать условиям выше: физический путь к Node.js 24 в `ExecStart`, отдельный `EnvironmentFile` и рабочая папка `current`. Способ первоначальной настройки зависит от установленной версии BrainyCP. Если панель создаёт иную службу, администратор должен отдельно согласовать конфигурацию; сценарий остановится, а не перепишет её.

Исполняемый файл Node.js и его родительские каталоги должны принадлежать root и быть недоступны для записи группе и остальным пользователям: часть проверок запускается с правами root. Runtime внутри каталога, изменяемого пользователем приложения, для этого сценария не подходит.

Прокси игры храните в `/etc/nginx/conf.d/DOMAIN-game.conf`; не правьте `sites-available`. Администратор отдельно проверяет, что этот файл подключён в Nginx, не создаёт конфликтующих виртуальных хостов с панелью, использует сертификат нужного домена, передаёт запросы на `127.0.0.1:PORT` и поддерживает WebSocket. Первичная настройка сертификата и проверка Nginx выполняются отдельно от выпуска приложения. Внешний доступ к порту Node.js и PostgreSQL не требуется.

### 2. Отдельная база PostgreSQL

Создайте отдельную БД и пользователя игры с одинаковым именем `ctokodnomy_USER_PORT`: для примеров этой инструкции — `ctokodnomy_appuser_3000`. Пользователь приложения должен владеть своей БД, чтобы применять миграции при запуске; права суперпользователя ему не нужны. Не меняйте роли и БД других сайтов. Если панель добавляет к имени свой префикс, такая установка не соответствует текущему адаптеру автоматического обновления.

Если панель не предоставляет создание PostgreSQL-БД, администратор может выполнить в интерактивной консоли `psql`:

```sql
CREATE ROLE ctokodnomy_appuser_3000 LOGIN;
\password ctokodnomy_appuser_3000
CREATE DATABASE ctokodnomy_appuser_3000 OWNER ctokodnomy_appuser_3000;
```

`\password` запрашивает пароль скрытым вводом. Используйте случайный пароль из 64 строчных шестнадцатеричных символов; это ограничение формата серверной конфигурации, а не пароля администратора игры. Для автоматического обновления PostgreSQL должен быть доступен на `127.0.0.1:5432`. Проект проверен с PostgreSQL 14 и 17; клиент `pg_dump` должен поддерживать установленную версию сервера.

### 3. Постоянные файлы и первый выпуск

Под пользователем приложения подготовьте каталоги `APP_ROOT/releases`, `APP_HOME/.config/ctokodnomy` и `APP_HOME/.local/share/ctokodnomy/PORT/uploads`. Используйте физический домашний каталог пользователя и каталоги без символических ссылок. Каталог `APP_HOME/.config/ctokodnomy` должен принадлежать пользователю приложения и иметь права `700`. Настройки, загрузки и резервные копии должны оставаться вне каталогов выпусков.

Создайте закрытый файл `APP_HOME/.config/ctokodnomy/native-PORT.env`, принадлежащий пользователю приложения, с правами `600`. Например:

```dotenv
NODE_ENV=production
CTOKODNOMY_MANAGED_CONFIG=1
HOST=127.0.0.1
PORT=3000
APP_ORIGIN=https://game.example.ru
DATABASE_URL=postgresql://ctokodnomy_appuser_3000:REPLACE_WITH_64_LOWERCASE_HEX_PASSWORD@127.0.0.1:5432/ctokodnomy_appuser_3000
MEDIA_DIR=/home/appuser/.local/share/ctokodnomy/3000/uploads
TRUST_PROXY=1
```

Замените маркер пароля на тот же случайный пароль из 64 строчных шестнадцатеричных символов, который задан роли БД. Файл не исполняют через `source` и не отправляют в переписку. `TRUST_PROXY=1` подходит для приложения, доступного только через доверенный локальный прокси и слушающего `127.0.0.1`. Метка `CTOKODNOMY_MANAGED_CONFIG=1` обозначает этот конкретный формат; её нельзя просто добавлять к несовместимой конфигурации.

**Actions → Build BrainyCP release (manual)** собирает артефакт `ctokodnomy-native`: архив, его SHA-256 и `COMMIT.txt`. Администратор проверяет контрольную сумму, распаковывает первый выпуск в новый `APP_ROOT/releases/COMMIT_SHA` и устанавливает production-зависимости командой `npm ci --omit=dev` под пользователем приложения с Node.js 24. Архив не содержит настроек, загрузок или `node_modules`.

Внутри выпуска нужна ссылка `.env` на постоянный файл настроек, а `APP_ROOT/current` должен указывать на этот выпуск. Первое создание ссылок и запуск выполняются администратором отдельно, без перезаписи существующих файлов. Для дальнейших обновлений используйте Actions, который проверяет подготовленную структуру.

### 4. Первый запуск и мастер установки

Запустите подготовленную службу игры и проверьте локальный `/api/health`, публичный HTTPS, WebSocket и PHP-сайты. Исправный `/api/health` отвечает `{"ok":true}`. При первом запуске приложение применяет миграции к своей БД.

Для первого входа выполните под пользователем приложения с физическим Node.js 24:

```sh
cd /home/appuser/sites/game/current
/physical/path/to/node24/bin/node dist/server/cli.js setup-token
```

Откройте `/setup`, введите выданный токен и создайте администратора. Токен действует час, выводится только в вашей консоли и не должен попадать в Actions, переписку или скриншоты. Настройте название, цвета и логотипы, затем проведите пробную игру с табло и телефонами обеих команд.

## Резервирование и восстановление

Перед мероприятием проверьте восстановление копии БД на отдельной тестовой БД и сохранение изображений во внешней копии. Не удаляйте прежний выпуск сразу после обновления. Автоматический возврат `current` восстанавливает прежний код, но запуск нового кода мог изменить схему БД. Восстановление старой БД теряет изменения после её копирования и требует отдельного решения администратора.

Состояние и журнал службы смотрите в BrainyCP. Для сброса пароля администратора выполните под пользователем приложения:

```sh
cd /home/appuser/sites/game/current
/physical/path/to/node24/bin/node dist/server/cli.js reset-password YOUR_ADMIN_USERNAME
```

CLI запросит новый пароль скрытым вводом и отзовёт существующие сеансы администратора.
