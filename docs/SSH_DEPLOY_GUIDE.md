# Памятка: SSH-ключ, Windows PowerShell и GitHub

Эта памятка сохраняет действия из нашей переписки и объясняет, зачем они нужны. Все команды с пометкой `powershell` выполняются на твоём Windows-компьютере в PowerShell.

Адреса в документе — примеры. Перед выполнением замени `server.example.com` на адрес своего сервера. Домен и сервер конкретного экземпляра задаются локально и в настройках размещения, а не в коде приложения.

## Что уже получилось

По результатам переписки на 14 октября 2026 года:

- На Windows создан ключ `C:\Users\a\.ssh\codex_deploy`.
- Его публичная часть добавлена на сервер `root@server.example.com`.
- Проверка входа именно новым ключом вернула `root`.
- По твоему сообщению, секрет `DEPLOY_SSH_KEY` добавлен в GitHub Actions Secrets. Его использование в сценарии деплоя ещё не проверено.

- Прямой SSH-доступ облачного Codex к серверу ещё не настроен.

## 1. Как устроен ключ

SSH — способ подключаться к серверу и выполнять на нём команды.

Одна пара ключей состоит из двух файлов:

| Файл | Для чего нужен | Где используется |
| --- | --- | --- |
| `codex_deploy` | Приватный ключ: подтверждает право на вход | На машине, которая подключается; для будущего деплоя — в GitHub Actions Secrets |
| `codex_deploy.pub` | Публичный ключ: разрешает вход соответствующим приватным ключом | На сервере в `/root/.ssh/authorized_keys` |

Приватный ключ нельзя коммитить в репозиторий или отправлять в чат. Команды и публичный отпечаток можно сохранять в документации.

В PowerShell `$env:USERPROFILE` означает папку твоего пользователя, сейчас это `C:\Users\a`. В командах, отправляемых на Linux-сервер, `~` означает домашнюю папку удалённого пользователя: для `root` это `/root`.

## 2. Создание ключа — один раз

**Этот шаг уже выполнен. Для обычного подключения повторять его не нужно.**

Команды для создания нового ключа:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh" | Out-Null
ssh-keygen -t ed25519 -C "codex-deploy" -f "$env:USERPROFILE\.ssh\codex_deploy"
```

- Первая команда создаёт папку `.ssh`, если её ещё нет.
- `ssh-keygen` создаёт пару ключей.
- `-t ed25519` задаёт тип ключа.
- `-C "codex-deploy"` добавляет подпись, чтобы узнавать ключ.
- `-f` задаёт путь к файлу приватного ключа. Публичный файл получит суффикс `.pub`.

На запрос `Enter passphrase` можно ввести придуманную парольную фразу, нажать Enter и повторить её. Символы при вводе не отображаются. Чтобы оставить фразу пустой, нажимают Enter на обоих запросах. Это фраза для защиты ключа, а не пароль сервера.

Если команда предлагает перезаписать существующий файл, ответь `n`, чтобы сохранить уже работающий ключ. Если у ключа есть парольная фраза, её использование нужно будет отдельно учесть в будущем сценарии автоматического деплоя.

## 3. Добавление публичного ключа на сервер — один раз

**Этот шаг уже выполнен. Он нужен для нового ключа или нового сервера. Повторный запуск добавит ещё одну запись.**

Для выполнения команды нужен уже работающий вход на сервер: прежний SSH-ключ или пароль пользователя `root`.

```powershell
$codexPublicKey = (Get-Content -Raw "$env:USERPROFILE\.ssh\codex_deploy.pub").Trim()
ssh root@server.example.com "umask 077; printf '\n%s\n' '$codexPublicKey' >> ~/.ssh/authorized_keys && ssh-keygen -lf ~/.ssh/authorized_keys"
```

Что происходит:

1. PowerShell читает публичный файл в переменную `$codexPublicKey`. `Trim()` убирает переводы строки по краям.
2. SSH подключается к серверу с уже имеющимся доступом.
3. `printf` добавляет публичный ключ с явными переводами строки, отделяя его от прежних записей.
4. `>>` дописывает файл, сохраняя имеющиеся ключи. `umask 077` ограничивает доступ к вновь создаваемому файлу владельцем.
5. `ssh-keygen -lf` показывает отпечатки ключей, распознанных в файле.

Команда рассчитана на созданный нами публичный файл с подписью `codex-deploy`. На этом сервере папка `.ssh` уже существует; её проверенные права — `700`, права файла `authorized_keys` — `600`.

Отпечаток нашего ключа:

```text
SHA256:ZaFMjTkNZ29RHhJFXNCidugze8MGk+XGimAIjJs0r4Q
```

Отпечаток — идентификатор публичного ключа, а не пароль.

Первый способ добавления через передачу файла в стандартный ввод SSH не дал распознаваемой записи нового ключа. Точная причина не установлена. Повторное добавление командой выше с явными переводами строки сработало.

## 4. Проверка входа — можно повторять

```powershell
ssh -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -i "$env:USERPROFILE\.ssh\codex_deploy" root@server.example.com "whoami"
```

- `-i` указывает приватный ключ на твоём компьютере.
- `IdentitiesOnly=yes` ограничивает набор предлагаемых ключей явно настроенными.
- `PreferredAuthentications=publickey` задаёт проверку через ключ без перехода к паролю учётной записи.
- `whoami` выполняется на сервере и показывает имя удалённого пользователя.

Если ключ защищён парольной фразой, SSH может попросить её ввести. Ожидаемый результат:

```text
root
```

Именно такой результат получен в твоём PowerShell. Это подтверждает доступ с Windows; ключ с твоего компьютера автоматически в облачной среде Codex не появляется.

При первом подключении с новой машины SSH может попросить подтвердить отпечаток ключа **сервера**. Сверь его через консоль хостинга. Это другой отпечаток, он не обязан совпадать с отпечатком `codex_deploy`.

## 5. Открытие ключа в Блокноте

Для просмотра и копирования приватного ключа:

```powershell
notepad "$env:USERPROFILE\.ssh\codex_deploy"
```

В Блокноте нажми **Ctrl+A**, затем **Ctrl+C**. Копируется весь текст, включая строки `BEGIN OPENSSH PRIVATE KEY` и `END OPENSSH PRIVATE KEY`. Для копирования менять и сохранять файл не требуется.

Если удобнее сразу скопировать ключ в буфер обмена:

```powershell
Get-Content -Raw "$env:USERPROFILE\.ssh\codex_deploy" | Set-Clipboard
```

## 6. Сохранение ключа в GitHub для будущего деплоя

1. Открой репозиторий `tsoyce/CTOKODNOMY` в GitHub.
2. Перейди в **Settings → Secrets and variables → Actions**.
3. Нажми **New repository secret**.
4. В поле **Name** введи `DEPLOY_SSH_KEY`.
5. В поле **Secret** вставь скопированный приватный ключ через **Ctrl+V**.
6. Нажми **Add secret**.

Сохраняется секрет для GitHub Actions. Само добавление секрета не запускает деплой и не предоставляет прямой SSH-доступ облачному Codex. Сценарий ручного деплоя находится в `.github/workflows/deploy.yml`; необходимые настройки и шаги описаны в [инструкции размещения](DEPLOYMENT.md).

Не путай два раздела GitHub:

| Раздел | Какой ключ добавляется | Зачем |
| --- | --- | --- |
| Secrets and variables → Actions | Приватный `codex_deploy`, как секрет `DEPLOY_SSH_KEY` | Чтобы будущий сценарий деплоя подключался к нашему серверу |
| SSH and GPG keys в настройках аккаунта | Публичный `codex_deploy.pub`, если нужен такой доступ | Чтобы выполнять Git-операции с GitHub через SSH |

## 7. Если снова появляется Permission denied

Проверить распознаваемые ключи и права на сервере, используя уже работающий обычный вход:

```powershell
ssh root@server.example.com "ssh-keygen -lf ~/.ssh/authorized_keys; ls -ld ~ ~/.ssh ~/.ssh/authorized_keys"
```

Показать важные строки диагностики подключения новым ключом:

```powershell
ssh -v -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -i "$env:USERPROFILE\.ssh\codex_deploy" root@server.example.com "whoami" 2>&1 | Select-String "Offering public key|Server accepts key|Load key|sign_and_send_pubkey|Authentications that can continue|Permission denied"
```

`Offering public key` показывает, какой ключ предлагает компьютер. `Server accepts key` означает, что сервер принял предложенный ключ на этапе проверки публичной части; окончательный результат проверяем по выполнению `whoami`.

Для разбора ошибки достаточно этих сообщений и публичных отпечатков. Приватный ключ и парольную фразу передавать не требуется.
