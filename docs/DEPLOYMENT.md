# Размещение и обновление приложения

В репозитории есть производственная сборка Docker Compose и ручной сценарий GitHub Actions. Он **не запускался на настоящем сервере** во время разработки. Организатор подтвердил добавление `DEPLOY_SSH_KEY` и сообщил, что на сервере уже работают другие сайты. Docker, свободные порты, ресурсы и конфигурация существующих сайтов ещё требуют проверки.

Все адреса ниже — примеры. Домен, сервер и путь конкретного экземпляра хранятся в серверном `.env` и настройках GitHub Actions; в коде приложения они не закреплены. Экземпляр можно перенести на другой домен изменением `APP_ORIGIN` и настройки reverse proxy.

## 1. Что проверить перед первым размещением

Подключитесь с Windows уже проверенным ключом:

```powershell
ssh -o IdentitiesOnly=yes -i "$env:USERPROFILE\.ssh\codex_deploy" root@server.example.com
```

В открывшейся Linux-консоли выполните читающие команды:

```sh
uname -a
df -h /
free -h
command -v docker
docker compose version
ss -ltnp
```

Проверьте, какие приложения уже размещены, как устроены Nginx/Caddy и HTTPS, и какой каталог выделен игре. Для сборки на сервере нужен запас памяти и диска: ориентир — 2 ГБ памяти и несколько ГБ свободного диска, фактическая потребность зависит от существующих сервисов. Если ресурсов мало, сборку образа можно перенести в CI отдельным изменением.

Нужны Docker Engine, Compose v2 с поддержкой `up --wait`, `tar`, `curl` и доступ сервера к Docker Hub/npm для сборки. Не заменяйте настройки существующих сайтов. Если Docker отсутствует, выберите и установите его по официальной инструкции для установленной ОС отдельно от запуска деплоя.

Для участников и гостей нужен адрес с HTTPS, например `https://game.example.ru`. Настройте DNS на сервер и сертификат в существующем reverse proxy. `example.ru` — пример, не заданный домен проекта. Внешние порты `3000` и `5432` открывать не требуется.

## 2. Подготовка отдельной папки и настроек

Пример каталога — `/opt/ctokodnomy`. Он должен быть выделен именно этому приложению. Если папка уже существует, сначала проверьте содержимое и владельца; не выполняйте команды поверх неизвестных файлов.

На сервере для новой папки:

```sh
mkdir -m 750 /opt/ctokodnomy
mkdir -m 700 /opt/ctokodnomy/shared
umask 077
nano /opt/ctokodnomy/shared/.env
```

В редакторе запишите настройки **самого сервера**:

```dotenv
POSTGRES_USER=ctokodnomy
POSTGRES_DB=ctokodnomy
POSTGRES_PASSWORD=REPLACE_WITH_A_GENERATED_HEXADECIMAL_PASSWORD
APP_ORIGIN=https://game.example.ru
COMPOSE_PROJECT_NAME=ctokodnomy
APP_PORT=3000
```

Замените пароль случайным значением, а адрес — настоящим HTTPS-адресом. Случайный пароль можно сгенерировать на сервере командой `openssl rand -hex 32`; не отправляйте его в чат и не сохраняйте в репозитории. Пароль БД передаётся контейнеру из `.env`, а не в аргументах удалённых команд. При изменении пароля уже инициализированного PostgreSQL правка `.env` сама по себе пароль роли в БД не меняет.

После сохранения:

```sh
chmod 600 /opt/ctokodnomy/shared/.env
```

Деплой использует этот файл без перезаписи. Если выбрано другое имя Compose-проекта или порт, проверьте отсутствие конфликтов. Имя проекта нельзя менять после первого запуска без переноса данных: от него зависят имена томов.

## 3. Настройки GitHub Actions

В репозитории откройте **Settings → Secrets and variables → Actions**.

В разделе **Variables** добавьте:

| Имя | Пример | Назначение |
| --- | --- | --- |
| `DEPLOY_HOST` | `server.example.com` | Проверенный адрес сервера |
| `DEPLOY_USER` | `root` | Пользователь с доступом к выделенной папке и Docker |
| `DEPLOY_PATH` | `/opt/ctokodnomy` | Абсолютный путь подготовленной папки без пробелов и завершающего `/` |

В разделе **Secrets** нужны:

| Имя | Значение |
| --- | --- |
| `DEPLOY_SSH_KEY` | Полный приватный ключ, уже добавлен по сообщению организатора |
| `SSH_KNOWN_HOSTS` | Проверенная строка с публичным ключом **сервера** |
| `DEPLOY_SSH_PASSPHRASE` | Парольная фраза приватного ключа, только если она задана |

Чтобы получить строку `SSH_KNOWN_HOSTS`, сначала сверьте отпечаток серверного ключа через доверенную консоль хостинга:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Затем по уже проверенному SSH-подключению прочитайте **публичный** ключ сервера:

```powershell
ssh root@server.example.com "cat /etc/ssh/ssh_host_ed25519_key.pub"
```

В секрет вставьте строку вида:

```text
server.example.com ssh-ed25519 AAAA...реальная_публичная_часть...
```

Берите тип `ssh-ed25519` и публичную часть из фактического вывода; вместо подписи в конце укажите в начале ровно `DEPLOY_HOST`. Это ключ сервера, он отличается от публичного ключа `codex_deploy.pub`. Деплой проверяет его строго и не доверяет результату непроверенного `ssh-keyscan`.

Сценарий использует GitHub Environment `production`. При необходимости настройте для него reviewers и ограничения ветки в **Settings → Environments**. Репозиторные Secrets доступны workflow; значения не нужно дублировать, если нет отдельной политики окружений. Официальные Actions сейчас указаны по стабильным major-тегам; для фиксации цепочки поставки их можно закрепить на предварительно проверенные SHA релизов.

## 4. Первое размещение

После проверки сервера, домена и настроек откройте **Actions → Deploy (manual) → Run workflow**, выберите ветку `main` и запустите сценарий.

Он сначала устанавливает зависимости по lockfile, проверяет типы, правила/API, сборку и браузерный сценарий на отдельной тестовой БД. Затем отправляет архив **проверенного коммита** через SSH, строит образ на сервере, создаёт резервную копию БД перед миграциями и ждёт исправного запуска приложения. После запуска проверяются подключение к БД, структура публичного API, HTML главной и доступность JavaScript интерфейса.

Серверные файлы размещаются так:

```text
/opt/ctokodnomy/
  shared/.env                  настройки, сохраняются между обновлениями
  releases/<commit SHA>/       код каждого выпущенного коммита
  current -> releases/<SHA>/   ссылка на последний успешно запущенный выпуск
  backups/before-<SHA>.dump    копия БД перед обновлением
  incoming/                   временные архивы
```

PostgreSQL и загруженные изображения находятся в постоянных Docker volumes. Приложение публикует порт только на `127.0.0.1`; БД порт наружу не публикует. Во время замены контейнера возможен короткий перерыв, поэтому обновляйте приложение до репетиции или между партиями.

Откройте для существующего HTTPS-сайта проксирование к `http://127.0.0.1:3000`. Пример **блока внутри уже настроенного Nginx server**:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 90s;
    client_max_body_size 3m;
}
```

Проверьте конфигурацию `nginx -t` до её перезагрузки. Сохраните действующие домены и настройки TLS. Браузер должен открывать ровно HTTPS-адрес из `APP_ORIGIN`; origin включает схему, имя хоста и порт при нестандартном порте, но не путь.

## 5. Мастер установки

На сервере после успешного первого деплоя:

```sh
cd /opt/ctokodnomy/current
export APP_IMAGE_TAG="$(basename "$(pwd -P)")"
docker compose --env-file /opt/ctokodnomy/shared/.env exec app node dist/server/cli.js setup-token
```

CLI выдаёт одноразовый токен с ограниченным сроком жизни. Откройте страницу установки сайта, введите его, создайте администратора и настройте название мероприятия и цвета. После создания администратора установка закрывается. Токен не нужно публиковать в скриншотах или переписке.

Затем подготовьте реальные вопросы, создайте пробную игру, откройте табло на проекторе и телефоны двух команд, назначьте капитанов. Проверьте правильный и неправильный ответ, перехват, паузу, исправление решения и восстановление после обновления страницы. Логотипы и фон принимаются в PNG/JPEG/WebP, каждый файл до 2 МБ.

## 6. Обновления, журнал и восстановление пароля

Новый push запускает проверки, но **не обновляет сервер**. Для обновления вручную запустите Deploy (manual). Развёртывание сериализовано: параллельные запуски ожидают друг друга.

Обычные команды на сервере, из `/opt/ctokodnomy/current` после установки `APP_IMAGE_TAG` как выше:

```sh
docker compose --env-file /opt/ctokodnomy/shared/.env ps
docker compose --env-file /opt/ctokodnomy/shared/.env logs --tail 100 app
docker compose --env-file /opt/ctokodnomy/shared/.env exec app node dist/server/cli.js reset-password YOUR_ADMIN_USERNAME
```

Сброс пароля выполняется администратором сервера через CLI. Замените `YOUR_ADMIN_USERNAME` именем учётной записи. CLI запросит новый пароль и скроет ввод; пароль должен содержать 8–128 символов. Его не передают через аргумент командной строки. Существующие сеансы администратора отзываются; после восстановления повторно войдите в интерфейс.

При ошибке проверки ключа сначала сверяйте `SSH_KNOWN_HOSTS` с консолью хостинга; не отключайте проверку хоста. Если ключ защищён фразой, убедитесь, что задан `DEPLOY_SSH_PASSPHRASE`. Если workflow сообщает о существующем каталоге выпуска, проверьте его и текущие контейнеры: повторная отправка того же коммита не перезаписывает файлы.

Ссылка `current` меняется только после успешных проверок. Если workflow остановился после запуска контейнеров, новый контейнер и миграции уже могли примениться; сохранение старой ссылки само по себе не возвращает прежний выпуск.

## 7. Резервные копии и откат

Резервная копия перед миграциями лежит на том же сервере и **не заменяет внешнее резервирование**. Сохраняйте копии БД и тома изображений в другом защищённом месте. Перед мероприятием проверьте восстановление на отдельной тестовой БД. Не удаляйте рабочие тома командой `docker compose down -v`.

Для ручной копии БД:

```sh
backup_file="/opt/ctokodnomy/backups/manual-$(date -u +%Y%m%dT%H%M%SZ).dump"
(set -o noclobber; umask 077; docker compose --env-file /opt/ctokodnomy/shared/.env exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_file")
```

Имя содержит время создания; `noclobber` запрещает перезапись существующей копии. Для изображений сохраняйте том `<COMPOSE_PROJECT_NAME>_uploads` штатными средствами Docker или системы резервирования; БД без соответствующих изображений не восстанавливает весь сайт.

Предыдущие исходники и Docker images сохраняются. Возврат к прежнему образу возможен **только после проверки совместимости схемы БД**: запуск нового приложения уже мог применить миграции. Сначала остановите игровую активность, сохраните текущее состояние и изучите миграции. Для совместимой БД выберите существующий предыдущий SHA:

```sh
export APP_IMAGE_TAG=PREVIOUS_COMMIT_SHA
docker compose --env-file /opt/ctokodnomy/shared/.env -f /opt/ctokodnomy/releases/PREVIOUS_COMMIT_SHA/compose.yaml up -d --no-build --wait app
```

После проверки здоровья вручную обновите ссылку `current` на этот выпуск. Восстановление старой копии БД может потерять действия после её создания, поэтому сценарий не делает этого автоматически. До подтверждённого восстановления не очищайте старые образы, выпуски и резервные копии.
